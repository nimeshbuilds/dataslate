# Airflow workflow integration

DataSlate connects an explicitly approved DAG on **Apache Airflow 3.4.0** to the Pipelines → Workflows view, API and CLI. Airflow owns schedules, task dependencies, concurrency and task retries. DataSlate records manual-trigger intent in PostgreSQL, sends at most one upstream trigger for each accepted run, then reconciles the exact upstream identity. It never creates a second scheduler.

## Prerequisites

- Existing Airflow 3.4.0 behind a trusted HTTPS root endpoint, with the public REST v2 API and a **versioned GitDagBundle**. The qualified Git provider is 1.0.1. A LocalDagBundle, or another unversioned bundle, cannot satisfy the pinned trigger contract.
- A reviewed DAG, exact Airflow DAG version number and immutable Git bundle revision. Airflow must report that version as current, unpaused and healthy before a trigger. Changing the DAG requires a reviewed binding update and policy version change.
- Two distinct Airflow credentials: a metadata reader mounted only in the DataSlate API; a trigger/read broker mounted only in the workflow controller. Configure the Airflow auth manager to grant only the approved DAGs. They are **Airflow API tokens**, not the user's DataSlate token and not DataSlate task credentials.
- A separate, stable DataSlate service principal for Airflow tasks that use the [DataSlate provider](../../integrations/airflow/README.md). Give it only the exact execution, publication and SQL bindings it needs. Review these task privileges independently of who may trigger the DAG.
- The existing production DataSlate OIDC/PostgreSQL profile, an immutable workflow-controller image built from `api/WorkflowControllerDockerfile`, and reviewed network routes.

The included example is an overlay, not a working deployment with credentials. Replace every identity, endpoint, IP, version and Secret reference. Use the same reviewed DataSlate release image digests as the rest of the chart. The controller default tag is a development placeholder; it is not a published release artifact.

```sh
helm template dataslate deploy/helm/dataslate --namespace dataslate \
  -f deploy/examples/eks-external.yaml \
  -f deploy/workflow/example-values.yaml \
  -f /secure/location/organization-values.yaml

python3 deploy/preflight/check.py --context isolated-eks \
  --namespace dataslate --release dataslate \
  -f deploy/examples/eks-external.yaml \
  -f deploy/workflow/example-values.yaml \
  -f /secure/location/organization-values.yaml
```

Rendering and preflight do not deploy resources or certify cluster readiness. Existing Airflow ownership is preserved. An optional managed-service profile must be installed separately after its own dependency, identity and recovery review.

## Credential and network boundaries

`workflow.credentials` names existing Secret keys. `readTokenSecret` and `triggerTokenSecret` must be different keys across all credential records; the chart rejects aliasing them. Optional `caSecret` adds private trust; certificate and hostname verification remain enabled. Projected files support token rotation without placing values in ConfigMaps, resources, UI or command lines. The API and controller use the same generated file path but receive different Secret projections. File paths themselves are generated by Helm; user-supplied paths are rejected.

The worker uses a separate ServiceAccount with token automount disabled and no Kubernetes RBAC. Its egress is DNS, PostgreSQL and exact approved Airflow destinations; the API receives a separate metadata-egress rule. Check the cluster's CNI, DNS, destination NAT and all additive NetworkPolicies: a rendered policy alone cannot prove isolation. `/healthz` and `/readyz` use internal port 8086; no public worker Service is created.

`metadataAccessAccepted: true` acknowledges that a binding exposes the DAG's task names, dependency graph, schedule, timing and bounded history of **all its scheduled and manual runs** to its allowed subjects. Manual DataSlate operation records remain private to their initiating identity. Neither surface returns Airflow conf, task logs, connections, source code, XComs or row data. Do not grant the binding if the shared operational metadata is sensitive.

A trigger grant does not impersonate the human in task code. Airflow executes under the DAG's configured task identity. For example, a privileged ingestion service principal can write a table even when the trigger user's SQL identity is read-only. Enforce and explain that separation in the organization's policy.

## Recovery and operations

Record the binding, reviewed DAG ID/version, immutable bundle version, policy version and idempotency key before triggering. The API requires this exact reviewed selection and rejects a changed binding before creating a request. Repeating the complete exact request under the same identity recovers the accepted operation. After a durable dispatch intent, uncertain transport results are handled by GET/readback only. DataSlate checks DAG, backend run ID, approved version/bundle and its own conf receipt before trusting observations. A final `unknown` outcome needs operator investigation; it is not proof that Airflow stopped. The observation deadline is not a remote kill deadline.

There is no cancel endpoint: changing an Airflow database state would not establish that its workers terminated. Use your Airflow operator runbook for actual interruption and investigate affected DataSlate operations individually. Clearing or retrying provider tasks retains their logical DataSlate operation; a deliberately new DAG run is required for a new execution. Do not reset checkpoints or delete publication mappings to recover an uncertain request.

Revoke user access by removing the subject or binding and rotating its policy version. Keep the controller and necessary credential projections available while accepted operations still need reconciliation. `workflow.enabled: true` with `bindings: []` supports revocation without silently removing the controller or its mounted credentials. Coordinate Airflow permissions with DataSlate deployment; no hot-reload or automatic external policy change is promised.

The [workflow contract](../../docs/implementation/workflow-contract.md) defines exact resources and limits. [Local qualification](../../docs/implementation/workflow-qualification.md) records real Airflow schedule/trigger observations and PostgreSQL/controller/browser checks. This is not EKS/S3, KubernetesExecutor, production Airflow OIDC, backfill, visual DAG editing or a complete self-contained platform certification.
