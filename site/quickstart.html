STEP 01

A small development setup.

You need Git, Go 1.27.1 (the version in api/go.mod), Node.js 22.19+ on the Node 22 line and npm. Python 3.11+ is optional for the SDK/CLI; Python 3.12 is used in CI. Docker and Kubernetes are unnecessary for editing and saving documents.

The commands below use a POSIX shell on macOS or Linux. On Windows, use a Linux development environment such as WSL. Keep ports 8080 and 5173 free.

Disposable development state. Explicit development mode provides a marked administrator and the default workspace. Storage is in memory and clears when the API stops. It refuses database configuration and non-loopback listening. Use the Kubernetes path for persistent, authenticated operation.

STEP 02

Start two terminals.

In terminal 1, clone the repository and leave the API running. All commands later in this guide start at this repository root unless a directory change is shown.

Terminal 1 · API
git clone https://github.com/NimeshBuilds/dataslate.git
cd dataslate
make dev-api

In terminal 2, open the dataslate checkout, then install the locked workspace dependencies and start Vite.

Terminal 2 · Workspace
cd web
npm ci
npm run dev
↗

Open http://127.0.0.1:5173Vite forwards the API to 127.0.0.1:8080. Keep both terminals running.

Use the exact loopback URL. Do not publish this mode through a reverse proxy, tunnel or public interface. If Vite prints a different port, free 5173 and restart it to follow this guide exactly.

STEP 03

Verify the real application.

In a third terminal, check the API. The status must identify DataSlate, authMode: development and persistence: memory.

Read-only checks
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
curl --fail http://127.0.0.1:8080/api/v1/status
curl --fail http://127.0.0.1:8080/api/v1/workspaces
  1. Select the default workspace and create a Python notebook or SQL document.
  2. Edit a cell, save it, reopen it and inspect saved revisions. Reloading the browser preserves server state while this API process remains running.
  3. Explore the module inventory, deployment plans and SparkApplication previews. These are configuration artifacts; they do not install services or submit a job.
  4. Check that unconfigured execution, SQL and Sylon explain which integration is missing. No sample result is presented as a completed operation.

Stop each development process with Ctrl + C. Export anything you need before stopping the API; in-memory documents are not recoverable afterward.

STEP 04

The same workspace, from your shell.

From the repository root, create an isolated Python environment. The CLI and SDK use the same API, resources and permissions as the browser.

SDK + CLI · Python 3.11+
python3 -m venv .venv
.venv/bin/python -m pip install ./sdk/python
.venv/bin/dataslate status
.venv/bin/dataslate workspace list
.venv/bin/dataslate notebook list --workspace default
.venv/bin/dataslate modules

The default API origin is http://127.0.0.1:8080. Set DATASLATE_API_URL for a different server. Production requires HTTPS and an API-audience access token through DATASLATE_API_TOKEN; the CLI has no interactive OAuth login yet. Supply tokens through your approved secret tooling, not command arguments or checked-in files. A private CA can be provided with DATASLATE_CA_FILE.

STEP 01

Make the ownership explicit.

This path configures a shared installation for teams in one organization, initially on EKS with S3. Start with an existing PostgreSQL database and IdP; the base chart deploys DataSlate's API, web application, migration Job, Services and network policies.

Production configuration ≠ production qualification. EKS/S3 identity, a real browser IdP login, effective isolation, capacity, failover and restore must pass on your installation before production use. Full-platform installation and upgrade coordination remain under development.
PrepareRequired configuration
WorkstationGit, Python 3.11+ with PyYAML, pinned Helm 4.3.0, a cluster-compatible kubectl, Docker Buildx and authenticated access to your registry. Source builds use the pinned Dockerfile toolchains. The database administration environment also needs the PostgreSQL psql client.
KubernetesCore APIs need 1.29+. The selected Apache Spark operator requires 1.34+; use a separately qualified cluster/version. A NetworkPolicy-enforcing CNI, dedicated namespace and restricted Pod Security are required.
IdentityHTTPS OIDC issuer, public browser client with Authorization Code + PKCE, a distinct API audience, workspace claims and exact HTTPS callback.
DatabaseDedicated PostgreSQL 17 database, trusted TLS, migration privileges, credential/CA Secrets and a tested backup/restore procedure. Optional CNPG needs its own reviewed operator and persistent storage.
NetworkDNS name, existing ingress controller, certificate/TLS termination, ingress source peers, database subnets and approved IdP egress.
Data lakeS3 object-storage prefixes and separate workload IAM/KMS grants for engines. EBS is database block storage, not the lake. Azure/GCP identity and storage require separate qualification.

Inspect existing operators and service ownership before enabling a managed profile. The application never adopts an existing database or upgrades shared CRDs automatically. The base API/web receive no S3 identity and no Kubernetes API token with execution disabled.

STEP 02

Build a release you can identify.

Clone the repository as in the development path, select the source revision you reviewed and build the API and workspace images. Example registry names are placeholders; this guide does not assume public DataSlate images exist. Replace the registry below with a repository you own. Authenticate using your registry's approved workflow.

Repository root · publishes to your registry
export DATASLATE_REGISTRY=registry.example.com/your-team/dataslate
export DATASLATE_REVISION=$(git rev-parse HEAD)

docker buildx build --platform linux/amd64 --push \
  -t "$DATASLATE_REGISTRY/api:$DATASLATE_REVISION" \
  -f api/Dockerfile api

docker buildx build --platform linux/amd64 --push \
  -t "$DATASLATE_REGISTRY/web:$DATASLATE_REVISION" \
  -f web/Dockerfile web

docker buildx imagetools inspect \
  "$DATASLATE_REGISTRY/api:$DATASLATE_REVISION"
docker buildx imagetools inspect \
  "$DATASLATE_REGISTRY/web:$DATASLATE_REVISION"

This example targets amd64 nodes. Select the platform matching your node pool, or build and qualify a multi-architecture image. Record the published sha256:… manifest digests in your values. Tags identify the source but can move; the Helm image digest is the release identity.

Build optional controller/runtime images only when enabling their profile; their Dockerfiles and contexts are listed in the linked deployment guides. Scan and verify the resulting artifacts according to your release policy. Configure registry pull credentials through an existing Secret and imagePullSecrets if required.

STEP 03

Connect identity and durable storage.

OIDC registration

  1. Register a public browser client, for example dataslate-web, with Authorization Code + PKCE. Register exactly https://YOUR_HOST/auth/callback and the allowed web origin. No browser client secret is used.
  2. Mint signed access tokens for a distinct audience, for example dataslate-api. Add the provider-specific API scope to oidc.scopes. An ID token for the browser is not an API access token.
  3. Map dataslate_roles and dataslate_workspaces in access tokens. A selected administrator needs platform-admin to create a workspace; that role alone does not grant workspace access.
Example access-token claims · configured in your IdP
{
  "sub": "your-stable-user-id",
  "dataslate_roles": ["platform-admin"],
  "dataslate_workspaces": {
    "WORKSPACE_ID_FROM_DATASLATE": "admin"
  }
}

After first login, create a workspace, assign its returned ID to the appropriate IdP users/groups with viewer, editor or admin membership, and obtain a fresh access token. Membership administration UI and group synchronization are not implemented. Use separate identities to verify allowed and denied access.

PostgreSQL and Secrets

Create a dedicated database, an owner/migration role and a separate restricted runtime login through your database administration process. The generated configuration isolates the owner credential in the migration Job; runtime Pods receive only their own Secret. The runtime role must not own the database or tables, have elevated flags or belong to other roles. Separate Secret names alone do not prove separate database identities.

The connection must use the database's real TLS DNS name and sslmode=verify-full. In the application namespace, supply these existing Secret references through your secret manager or the repository runbook's file-based procedure:

SecretKeyContents
dataslate-runtime-databasedatabase-urlPrivate runtime-role PostgreSQL URI; credentials correctly URI-encoded.
dataslate-migration-databasedatabase-urlSeparate owner/migration-role URI for the same database.
dataslate-database-caca.crtTrusted PEM CA chain for the database certificate.

If the IdP uses an organizational CA, set the optional oidc.caSecret reference. That trust bundle is used for issuer discovery and JWKS only; browsers and command-line clients need their own appropriate trust configuration.

Never place the database URL or tokens in Helm values, shell arguments, Git or diagnostic output. Create the namespace before adding Secrets. The namespace example supplies restricted Pod Security labels for a new namespace; review labels rather than overwriting an existing namespace.

Optional managed PostgreSQL requires the separate CNPG bootstrap, an explicit storage class and managed database overlay. Its retained volumes are not backups; backup/restore and availability remain release gates.

STEP 04

Give every dependency real coordinates.

The offline setup generator prepares a review bundle with your exact coordinates. Its initial profile uses existing external PostgreSQL and an in-cluster ingress controller terminating a TLS Secret. It performs no Kubernetes calls, creates no credentials and leaves engines disabled. The internal ALB/ACM example is a separate manually configured ingress alternative; do not mix its external load-balancer CIDRs with this profile's pod selectors.

Install Python/PyYAML and the checksum-pinned Helm binary, then copy the non-secret profile into a private working directory. The Helm fetch helper supports macOS arm64 and Linux amd64; on other platforms set DATASLATE_HELM to your separately verified Helm 4.3.0 executable.

Repository root · local configuration tooling
python3 -m venv deploy/.cache/venv
deploy/.cache/venv/bin/python -m pip install -r deploy/tests/requirements.txt
deploy/.cache/venv/bin/python deploy/scripts/fetch-helm.py
export DATASLATE_HELM="$PWD/deploy/.cache/helm"

umask 077
export DATASLATE_CONFIG="$HOME/.config/dataslate"
mkdir -p "$DATASLATE_CONFIG"
cp -n deploy/setup/profile.example.json "$DATASLATE_CONFIG/profile.json"

Edit profile.json with your real values before continuing. The copy command preserves an existing file. Use namespace: dataslate and release: dataslate to match the examples on this page, or follow your generated runbook's exact names. All image digests, DNS names, network ranges and identity/Secret references in the example profile must be reviewed and replaced. It contains references only, never credentials. Generate a new review bundle · no cluster changes
export DATASLATE_REVIEW="$DATASLATE_CONFIG/review-v1"
deploy/.cache/venv/bin/python deploy/setup/generate.py \
  --config "$DATASLATE_CONFIG/profile.json" \
  --output "$DATASLATE_REVIEW" \

The output directory must not already exist. Review all five files: values.yaml, namespace.yaml, prerequisites.json, rendered-core.yaml and RUNBOOK.md. The runbook uses your selected context, names and database roles. Generated files do not prove the images, credentials, identities or network routes actually work.

All engine controllers are opt-in. Leave them disabled until their service, credentials, grants and network policies are ready. Standard NetworkPolicy is additive and cannot allowlist DNS names; verify the actual CNI, DNS, SNAT/DNAT and ingress behavior.

Existing services stay externally owned. PostgreSQL, identity, ingress, registry, lake storage and operators are not installed by the base chart. Installing a managed component is a separate reviewed action, even if a compatible service is detected.

STEP 05

Render first. Inventory the exact cluster.

The generator already renders the core chart locally. Review its manifest and prerequisite list before accessing Kubernetes. Set the context to the same exact context in your profile; preserve your generated RUNBOOK.md as the installation record.

New namespace only · changes the selected cluster
export DATASLATE_CONTEXT=your-reviewed-kube-context
export DATASLATE_VALUES="$DATASLATE_REVIEW/values.yaml"

kubectl --context "$DATASLATE_CONTEXT" get namespace dataslate
# Only if it does not exist and this is a new installation:
kubectl --context "$DATASLATE_CONTEXT" create \
  -f "$DATASLATE_REVIEW/namespace.yaml"
"$DATASLATE_HELM" list --kube-context "$DATASLATE_CONTEXT" \
  --namespace dataslate --all

A genuinely new namespace should return NotFound on the first read; a forbidden or unavailable response does not establish absence. create must stop if the namespace exists. Do not overwrite its labels, delete it or adopt an existing release automatically. Provision every named Secret in prerequisites.json through your approved secret workflow after the namespace exists.

Creating the required Secrets from protected files

If you are not using a secret-management controller, an authorized administrator can create the example Secret references below from existing private files. Prepare each database URI file through your approved credential workflow; keep these files outside the repository with owner-only access. Match names/keys to your profile. The registry file is a Docker authentication config, and the TLS certificate must cover your workspace hostname.

New Secret references · replace all file paths
export DATASLATE_SECRET_FILES=/secure/config/dataslate-secrets

kubectl --context "$DATASLATE_CONTEXT" -n dataslate create secret generic \
  dataslate-runtime-database \
  --from-file=database-url="$DATASLATE_SECRET_FILES/runtime-database-url"
kubectl --context "$DATASLATE_CONTEXT" -n dataslate create secret generic \
  dataslate-migration-database \
  --from-file=database-url="$DATASLATE_SECRET_FILES/migration-database-url"
kubectl --context "$DATASLATE_CONTEXT" -n dataslate create secret generic \
  dataslate-database-ca \
  --from-file=ca.crt="$DATASLATE_SECRET_FILES/postgres-ca.pem"
kubectl --context "$DATASLATE_CONTEXT" -n dataslate create secret tls \
  dataslate-ingress-tls \
  --cert="$DATASLATE_SECRET_FILES/workspace.crt" \
  --key="$DATASLATE_SECRET_FILES/workspace.key"
kubectl --context "$DATASLATE_CONTEXT" -n dataslate create secret generic \
  dataslate-registry --type=kubernetes.io/dockerconfigjson \
  --from-file=.dockerconfigjson="$DATASLATE_SECRET_FILES/registry.json"

These commands create new objects and fail if a name already exists. Do not replace existing credentials implicitly. Omit the registry Secret only if your image access needs no credentials and you removed its reference from the profile. For a private IdP, provision the separate CA Secret named by oidc.caSecret with the configured key. Secure creation does not establish rotation or actual credential validity; test those separately.

Use the exact same values layers for rendering, preflight and installation. Keep generated manifests and reports private: they contain operational metadata.

Local render + read-only cluster preflight
"$DATASLATE_HELM" template dataslate deploy/helm/dataslate \
  --namespace dataslate --kube-version 1.34.0 \
  -f "$DATASLATE_VALUES" > "$DATASLATE_CONFIG/reviewed-final.yaml"

deploy/.cache/venv/bin/python deploy/preflight/check.py \
  --helm "$DATASLATE_HELM" \
  --context "$DATASLATE_CONTEXT" \
  --namespace dataslate --release dataslate \
  -f "$DATASLATE_VALUES"

Set --kube-version to your reviewed target version. Managed CNPG rendering additionally needs --api-versions postgresql.cnpg.io/v1/Cluster. Managed/execution preflight also needs the exact existing operator Deployment names described in the preflight runbook.

Preflight exit codes

0
All recorded prerequisites observed.
1
A definite blocker was found; resolve it.
2
Invalid command, configuration or render.
3
Unresolved prerequisites or live checks remain. Read every finding; this is not production readiness.

The checker never installs or adopts resources. It may require named Secret-read permission to observe required key names; kubectl receives the full Secret before emitting keys, so run it only in a trusted administrator environment. It cannot establish actual network enforcement, cloud identity or backend health.

STEP 06

Install, sign in and prove persistence.

Follow the generated RUNBOOK.md after resolving inventory blockers and reviewing ownership. The commands below are for a new release named dataslate. The database, namespace, referenced Secrets and infrastructure must already exist. Install first without waiting for API readiness: the runtime role deliberately has no application-table grants until the schema exists.

New release · wait for migration only
"$DATASLATE_HELM" install dataslate deploy/helm/dataslate \
  --kube-context "$DATASLATE_CONTEXT" \
  --namespace dataslate -f "$DATASLATE_VALUES" --timeout 10m

kubectl --context "$DATASLATE_CONTEXT" -n dataslate \
  wait --for=condition=complete job/dataslate-migrate-1 --timeout=10m

The normal release Job applies the embedded schema as the migration role. A migration failure must be investigated before proceeding. Do not use --atomic as a database rollback mechanism, or the initial -migrate-1 Job name for an upgrade.

From an approved PostgreSQL administration environment, configure a libpq service named dataslate-migration with the actual database, migration identity, sslmode=verify-full, trusted sslrootcert and an owner-only password file. Do not pass a password or connection URL on the command line. Match these non-secret role/database arguments to your profile:

After migration · grant runtime access
PGSERVICE=dataslate-migration psql -X -v ON_ERROR_STOP=1 \
  -v database=dataslate \
  -v migration_role=dataslate_migrator \
  -v runtime_role=dataslate_runtime \
  -f deploy/setup/runtime-role.sql

The script validates the role boundary and grants existing application tables and sequences, leaving the migration ledger read-only. It does not create users, assign passwords or change ownership. Rerun it after each schema migration; no automatic default privileges are configured.

Wait for the application, then verify HTTPS
kubectl --context "$DATASLATE_CONTEXT" -n dataslate \
  rollout status deployment/dataslate-api --timeout=10m
kubectl --context "$DATASLATE_CONTEXT" -n dataslate \
  rollout status deployment/dataslate-web --timeout=10m
kubectl --context "$DATASLATE_CONTEXT" -n dataslate \
  get jobs,pods,pdb,networkpolicy

deploy/.cache/venv/bin/python deploy/scripts/verify-install.py --url https://YOUR_HOST
  1. The HTTP verifier must report 200 for web/API health, readiness and OIDC configuration, and 401 for anonymous API status. For a private workspace CA, append --ca-file /secure/config/workspace-ca.pem to the verifier command. Browser trust is configured separately; never disable verification.
  2. Complete an actual PKCE login. Create the first workspace, assign its ID in your IdP and sign in with a fresh access token.
  3. Create/save/reopen a document. Verify it survives an approved API rolling restart. Check a viewer cannot edit, another workspace cannot read it, and an expired access token fails.
  4. Verify isolation, migration recovery, backups, restoration and resource budgets in your staging environment before allowing production workloads.
Local core installation evidence is available. The generated core release has run on isolated ARM64 k3s 1.35 with PostgreSQL 17.11 and separate migration/runtime identities. Real Keycloak 26.8.2 browser PKCE login, workspace authorization denials, trusted HTTPS ingress and a CNI-enforced denial of API access from an unlabelled Pod passed. Post-restart checks recovered the saved notebook’s exact content and revision after PostgreSQL and both API Pods restarted; a transient login failure required a retry. See the qualification record and tested release path. This does not qualify EKS/S3, optional engine deployments, complete-platform installation, capacity, upgrades or backup restoration.

The UI, API and CLI share authorization. Notebook access is not data-row authorization: lake permissions and SQL policies must be enforced by the selected engines, and arbitrary Python with raw storage access can bypass SQL row filters.

STEP 08

Operate the whole system.

Backups + restoration

Protect PostgreSQL, lake metadata, data/checkpoints and configuration through their owners' backup mechanisms. Test a clean restore with compatible schema, extensions, credentials and runtime images. Retained PVCs alone are not a restore plan.

Upgrades + rollback

Review source/image/profile changes, restore a backup into staging and test migrations before changing production. Use an explicit Helm upgrade, wait for that release revision’s migration Job, rerun runtime grants, then verify readiness. Helm rollback does not reverse schema migrations or lake writes. Shared operators/CRDs follow their own upgrade procedures.

Credential rotation

Rotate through your secret manager. Environment-backed database credentials require Pod rollout; mounted credentials and cached clients need their documented refresh checks. Airflow API JWT renewal is an external operational prerequisite.

Runs + uncertain outcomes

Retain the same complete request and idempotency key after a lost response. A timeout is not a cancellation. Keep controllers and permissions until execution, cancellation and artifact cleanup have been observed.

Capacity + monitoring

Monitor readiness, migration failures, reconciliation age, backend queues, quotas and storage growth. Tune requests/limits and test peak load. Replicas and PDBs help planned disruption; they do not establish an availability SLA.

Decommissioning

Drain workloads and verify cleanup before removing controllers. Uninstalling the workspace does not undo lake writes, remove external services or cancel all jobs. Managed CNPG may be retained by policy and needs a deliberate ownership plan.

WHEN SOMETHING FAILS

Start with the failing boundary.

The local workspace cannot reach the API.

Confirm both development processes are running and curl --fail http://127.0.0.1:8080/readyz succeeds. Use the literal loopback URL on port 5173. Free occupied ports and restart Vite. Development mode refuses database configuration and public listening.

Pods are pending or images will not pull.

Check node capacity, architecture, scheduling rules, quotas, registry reachability and existing image-pull Secret references. Compare the configured digest with the published image. A placeholder image or an amd64-only image on arm64 nodes cannot become a working deployment.

The API stays unready or the migration Job fails.

Check Job/Pod events and carefully reviewed logs for DNS, network policy, database permissions, CA trust and hostname mismatch. Confirm the Secret key names match the values and PostgreSQL uses verified TLS. Do not print the database URL or bypass certificate verification. Increasing the timeout cannot fix a bad dependency.

Login succeeds, but API requests return 401 or 403.

For 401, verify issuer, signature, expiry, audience, access-token type and API scopes. The browser client ID must differ from the API audience. For 403, verify the exact workspace ID and role claims, then obtain a fresh token. Platform administrator does not imply workspace membership.

Preflight returns 3.

Read the report's unresolved prerequisites and live checks. Exit 3 deliberately means it cannot conclude readiness; read-only inventory cannot prove network enforcement, IdP login or a data-plane operation. Resolve or separately qualify every applicable finding.

An engine, query or Sylon action is unavailable.

The base chart leaves integrations disabled. Check the exact versioned binding, current workspace/subject grants, controller readiness, Secret references, endpoint TLS and allowed network path in that integration's runbook. Do not substitute a new request key to repair an uncertain accepted operation.

The website roadmap still shows work remaining.

The roadmap distinguishes working code, bounded tests and live qualification. Installing a profile does not complete every engine, interactive, agent or operations feature. Follow the linked capability inventory and validation evidence for the current boundary.
