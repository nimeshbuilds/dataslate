**Cloud storage and dataset interoperability research**

Research snapshot: September 24–25, 2026. This is a proposed qualification plan based on primary documentation and tagged source inspection. No cloud deployment, credential exchange, integration test or benchmark was run. It extends the Kubernetes lakehouse blueprint for the user's requirement to connect existing data lakes and publish platform-ingested data as Delta Lake with Snappy-compressed Parquet data files.

**Use cloud object storage for the lake.** AWS S3, Azure Blob Storage/ADLS Gen2, and Google Cloud Storage are the corresponding services. Azure's “block blob” terminology does not mean an attached block device. EBS, Azure Managed Disks and GCP Persistent Disk/Hyperdisk instead serve database PVCs, local caches, shuffle and other component-specific needs. The lake should be accessed through certified storage connectors, not presumed to be a generic POSIX mount. [S3 objects](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingObjects.html), [Azure Blob and Data Lake Storage](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-blobs-introduction), [Cloud Storage overview](https://docs.cloud.google.com/storage/docs/introduction).

The same Delta table format can sit on all three clouds; its filesystem/IO connector, authentication, endpoint and commit coordination differ. Catalog metadata and the object store are separate dependencies. Glue is not automatically required for an AWS deployment, nor is a cloud-specific catalog automatically required on Azure/GCP. Retain one authoritative catalog/commit owner per table, while allowing the UI to present several existing catalogs.

| Storage profile | Spark access path | Recommended workload identity | Qualification requirements |
|---|---|---|---|
| AWS S3 | Hadoop S3A, usually `s3a://bucket/prefix` internally | Narrow IAM role using an appropriate supported SDK provider; IRSA/WebIdentity or EKS Pod Identity where compatible | Region/endpoint, SDK/Hadoop matching, driver and executor token refresh, KMS, commit coordination, cross-account policy |
| Azure ADLS Gen2 | Hadoop ABFS, `abfss://container@account.dfs.core.windows.net/prefix` | Microsoft Entra workload federation through the ABFS workload identity provider | HNS-enabled profile first, RBAC/ACL traversal, token audience and refresh, private networking, server versus workload identity paths |
| Google Cloud Storage | Google Hadoop connector, `gs://bucket/prefix` | GKE Workload Identity Federation; external Kubernetes federation with Application Default Credentials where qualified | Connector/auth-library versions, projected token refresh, IAM scope, KMS, generation/commit semantics |
| S3-compatible existing lake | Certified endpoint and S3A configuration | Endpoint-supported scoped credentials | A separate conformance profile for each supported storage implementation; S3 API compatibility alone does not establish transaction safety |

Hadoop's current S3A authentication documentation lists AWS SDK v2 credential providers including WebIdentity and container credentials. The Azure connector documents OAuth, workload identity and SAS providers. Pin these libraries to the runtime rather than install whichever cloud SDK is newest. [S3A authentication](https://hadoop.apache.org/docs/current/hadoop-aws/tools/hadoop-aws/authentication.html), [ABFS authentication](https://hadoop.apache.org/docs/current/hadoop-azure/index.html).

Kubernetes need not be hosted on the same cloud as the lake. Entra explicitly supports federation from AKS, EKS, GKE and on-premises Kubernetes. Google documents federation from AKS, EKS and self-hosted Kubernetes; GKE has a distinct managed federation integration. AWS supports OIDC trust and short-lived credentials through STS. Cross-cloud operation still needs connectivity, audience/issuer configuration, key rotation, scoped trust and measured transfer cost/latency. Prefer scheduling near the lake by default. [Microsoft federation](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation), [Google external Kubernetes federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-kubernetes), [GKE federation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity), [AWS OIDC trust](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-idp_oidc.html).

For the GCS connector, explicitly select the qualified authentication mode: its current configuration supports `APPLICATION_DEFAULT`, `COMPUTE_ENGINE`, token-provider and other modes. A static JSON service-account key should be an optional compatibility path, not our preferred production onboarding flow. [GCS connector configuration](https://github.com/GoogleCloudDataproc/hadoop-connectors/blob/master/gcs/CONFIGURATION.md).

**Catalog credential vending and direct workload credentials require separate certification.** UC's Spark documentation supports S3, ADLS and GCS configuration, but examples are not proof that every cloud workload identity route works through every UC server version. For example, its Azure configuration example uses client credentials; ABFS having a workload identity provider does not automatically establish that UC's Azure vending service uses that provider. Test both the server's identity used to vend credentials and the scoped credentials consumed by actual engines. Never give an RLS-restricted notebook a broad fallback cloud identity. [UC Spark/storage integration](https://github.com/unitycatalog/unitycatalog/blob/main/docs/integrations/unity-catalog-spark.md).

**Represent storage, files, tables and compression separately.** JSON is a serialization format, Parquet is a columnar file format, Snappy is a compression codec, and Delta/Iceberg are table formats that track a transactional collection of files. A Delta table cannot be correctly read by listing every `.parquet` file beneath its directory; this can include removed files and bypass table features. An Iceberg table must follow its catalog pointer and snapshot/manifest metadata, including applicable delete files. [Delta protocol](https://github.com/delta-io/delta/blob/v4.4.0/PROTOCOL.md), [Iceberg specification](https://iceberg.apache.org/spec/).

The UI's discovery service should expose the following states: connection verified → permitted prefixes/catalogs scanned → candidate dataset → format verified → schema reviewed → asset registered. This is our proposed workflow, not a claim that an existing component implements it in full.

| Existing dataset | Proposed behavior |
|---|---|
| JSON/JSON Lines, CSV, text | Sample within a scan budget, surface parsing options, proposed schema, malformed records and confidence. Do not silently infer a universal schema from the first file. |
| Plain Parquet, including Snappy or Zstd | Read footer/schema metadata with bounded requests, validate incompatible schemas and partition conventions; compression is detected per file/column chunk. |
| Delta | Load with the Delta reader and validate protocol/table features. For catalog-managed tables, use the managing catalog; raw-path discovery is not an access substitute. |
| Iceberg | Attach to the existing authoritative catalog and identify current metadata/snapshot. Do not select a “latest” metadata JSON by object modification time or register a second writable catalog automatically. |
| ORC/Avro and additional formats | Add qualified reader profiles through the same interface; expose read, write, streaming and SQL capabilities separately. |
| Mixed, damaged or unfamiliar content | Show the detected candidates and limitation; leave unrecognized content as files until a supported reader/schema is configured. |

Spark already offers JSON schema inference and parsing modes, and Parquet schema/partition support. These are useful primitives; the product must supply bounded scanning, schema contracts, catalog registration, permissions and explainable discovery results. [Spark 4.1.3 JSON](https://spark.apache.org/docs/4.1.3/sql-data-sources-json.html), [Spark 4.1.3 Parquet](https://spark.apache.org/docs/4.1.3/sql-data-sources-parquet.html).

Record an asset's owner, storage location, authoritative catalog, table UUID, protocol/features, schema fingerprint, source of discovery, last successful verification and supported execution profiles. Automatic discovery must not rewrite existing data, enable table features, adopt maintenance ownership, or expose new assets broadly. Poll catalog changes; use optional cloud object notifications plus periodic reconciliation for file sources. Discovery events are hints, not transaction commits.

**Default platform ingestion to Delta with an explicit Snappy policy.** For new platform-owned outputs, persist `format=delta`, `data_file_format=parquet`, and `compression=snappy` in the pipeline/table policy. Configure certified Spark writes explicitly and verify the resulting Parquet footer codecs. Enforce the same choice in compaction and maintenance writers; a codec change affects future files unless data is rewritten. The Delta log/checkpoints are not all Snappy Parquet data files.

Upstream Spark's Parquet codec default is Snappy and supports other codecs. Delta 4.4's write implementation passes the `compression` option to its Parquet writer. This makes the requested output practical without a custom file format. [Spark compression configuration](https://spark.apache.org/docs/4.1.3/configuration.html), [Delta 4.4 write options](https://github.com/delta-io/delta/blob/v4.4.0/spark/src/main/scala/org/apache/spark/sql/delta/files/TransactionalWrite.scala).

Do not describe Snappy as today's universal Databricks managed-table default. Databricks changed newly created managed tables on Runtime 16.0+ to Zstd in October 2025. We can honor the requested Snappy default while offering Zstd as an explicit, benchmarked policy. Existing connected datasets keep their formats and codecs. [Databricks October 2025 release notes](https://docs.databricks.com/aws/en/release-notes/product/2025/october).

Kafka ingestion should use a qualified Structured Streaming source-to-Delta path with a stable per-pipeline checkpoint, explicit parsing/schema handling and recorded source metadata. A general-purpose Kafka object-store sink that only writes Parquet is not thereby a Delta sink. Connector batch jobs can stage immutable files and manifests, then use a platform-controlled Spark publication job. Keep source offsets/checkpoints separate from table metadata and do not delete them as generic “metadata cleanup.” [Delta streaming](https://docs.delta.io/delta-streaming/).

**Commit safety is the main cloud-specific gate.** Prefer qualifying new platform-owned ingestion tables as UC catalog-managed Delta through the current UC Delta API. In that mode, the catalog ratifies commits and clients must use the catalog to discover current table state. This can supply a common coordination model across clouds, but adds an availability, authorization and recovery boundary to certify. Catalog-managed table support is a protocol feature, not just registering an external table name in UC. [Catalog-managed Delta](https://docs.delta.io/delta-catalog-managed-tables/), [UC Delta API introduction with OSS UC](https://delta.io/blog/2026-07-03-unity-catalog-delta-api/).

Existing external/path-based Delta tables retain their established commit protocol. Current Delta storage guidance still documents a default single-driver S3 path and an experimental multi-cluster DynamoDB LogStore path; the latter requires all writers to use the same coordination table and region. The tagged Delta 4.4 `S3SingleDriverLogStore` uses a JVM-local path lock and Hadoop file creation, so the class's name and contract cannot be treated as multi-driver synchronization. [Delta storage configuration](https://docs.delta.io/delta-storage/), [Delta 4.4 S3 LogStore source](https://github.com/delta-io/delta/blob/v4.4.0/storage/src/main/java/io/delta/storage/S3SingleDriverLogStore.java).

The storage guide's explanation that S3 has no conditional creation mechanism is outdated: S3 now documents conditional writes. That service capability does not prove the selected Hadoop/Delta writer actually uses it safely. Certify the exact writer, filesystem and coordination profile; do not “fix” the problem by assuming strong consistency or by adding a product database lock that external writers ignore. For Azure and GCS the storage guide documents concurrent-write guarantees with supported filesystem implementations, which likewise require exact-runtime testing. [AWS conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

**Correction to the earlier UniForm assessment.** It is too broad to describe all current UniForm metadata conversion as asynchronous. Delta 4.3 release notes announce atomic and incremental conversion; Delta 4.4 adds atomic initialization. The 4.4 UniForm module supports Spark 4.1, not Spark 4.2. [Delta 4.3 release](https://github.com/delta-io/delta/releases/tag/v4.3.0), [Delta 4.4 release](https://github.com/delta-io/delta/releases/tag/v4.4.0).

Source inspection confirms a precommit conversion path in Delta 4.4 `OptimisticTransaction`: it generates Iceberg metadata before committing and carries its location/converted Delta version in transaction information when the catalog table path applies. A separate `IcebergConverterHook` still includes synchronous and asynchronous postcommit conversion paths. Therefore freshness depends on version, table features, catalog and execution path. Metadata file generation, catalog ratification/publication, and reader cache refresh are distinct stages to validate; no general promise of immediate cross-engine visibility follows from a release-note phrase. [Tagged transaction source](https://github.com/delta-io/delta/blob/v4.4.0/spark/src/main/scala/org/apache/spark/sql/delta/OptimisticTransaction.scala), [Tagged conversion hook](https://github.com/delta-io/delta/blob/v4.4.0/spark/src/main/scala/org/apache/spark/sql/delta/hooks/IcebergConverterHook.scala).

UniForm is not two independent writable table formats sharing files. Keep the Delta writer authoritative; prevent Iceberg writers or cleanup jobs from modifying a Delta-owned table. Preserve read-version mapping and display “Delta committed” versus “available to this reader” when the verified path needs it. [UniForm limitations](https://docs.delta.io/delta-uniform/).

**Required certification before advertising a cloud/format profile.**

1. Read a customer-like existing lake without mutation; verify JSON variants, Parquet codecs, nested schemas, partition evolution and supported Delta/Iceberg features.
2. Create a fresh managed table, append, merge/update/delete, compact, and query through every supported notebook/SQL path. Validate row counts, values, snapshots, publication and actual data-file codec.
3. Launch two independent writers and inject a failure after data upload, before catalog ratification, and after ratification but before acknowledgement. Demonstrate conflict/recovery behavior and no blindly repeated append.
4. Exercise token expiry and rotation during long-running streaming jobs on drivers and executors; wrong issuer, audience, namespace, service account and storage prefix must fail closed.
5. Test cloud encryption permissions, private DNS/endpoints, proxy/CA configuration, transient errors, clock skew, region placement and result-cache identity boundaries.
6. Test platform and external writers together only under a shared supported commit protocol. Otherwise make the attachment read-only or explicitly restrict writer ownership.
7. For UniForm, verify create, append, schema change, delete, retry, reader cache refresh and failed publication through the real UC endpoint. For native Iceberg, follow the actual catalog/snapshot and honor delete semantics.
8. Maintenance requires explicit ownership of the asset. Imported lakes begin in observe-only mode; deletion/expiration jobs run only with a configured retention contract and compatible table client. Object-store lifecycle rules must not independently remove live data/log/checkpoint files.

These gates should produce a versioned compatibility matrix, not a universal “all datasets” badge. The intuitive product promise is that users connect a lake, see what works, and receive a clear action for unsupported features without discovering missing JARs or unsafe commit behavior through production failures.
