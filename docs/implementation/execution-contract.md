# Approved application and saved Python batch execution contract

DataSlate persists and reconciles **administrator-approved immutable Python applications** and opt-in **saved Python notebook batches** through the Apache Spark Kubernetes Operator. Both use the same durable runs, explicit identity grants, cancellation and ownership checks. Automated tests and a disposable local Kubernetes qualification cover these paths; this is not EKS/S3 production qualification. Interactive notebook kernels, per-cell results, SQL execution, user parameters, supplementary packages and result-table publication remain separate capabilities.

## Provisioned execution identities

Set `DATASLATE_EXECUTION_BINDINGS_FILE` to a mounted JSON file. Its root is an array of bindings. The API loads configuration at startup and requires a restart to change; the controller reloads it on each reconciliation and before submission. Production API configuration validates each grant's issuer against the configured OIDC issuer. The file contains public identity identifiers and runtime references, never credentials:

```json
[
  {
    "id": "approved-ingestion",
    "workspaceId": "ws-example",
    "name": "Approved ingestion application",
    "operator": "apache",
    "image": "registry.example.com/data/ingest@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "mainApplicationFile": "local:///opt/spark/app.py",
    "namespace": "dataslate-jobs",
    "serviceAccount": "approved-ingestion",
    "executorInstances": 2,
    "maxRunSeconds": 3600,
    "allowedSubjects": [
      {"issuer": "https://identity.example.com", "subject": "immutable-user-id"}
    ]
  }
]
```

The digest above is a placeholder, not a runnable image. The administrator must supply and qualify a real image, application and least-privilege service account. For the default `executionKind: "approved-app"` (also used when omitted), only `local:///` Python entrypoints inside a SHA-256-pinned image are accepted; mutable S3 application paths are rejected for execution. An explicit `executionKind: "notebook-python-batch"` instead requires `mainApplicationFile` to be omitted or empty and uses a server-generated immutable source snapshot mounted at a fixed driver path. Spark 4.1.3 and Apache operator 1.0.0 are the candidate compatibility profile. Driver/executor templates use restricted security contexts and numeric UID/GID 185; custom images must support that identity. Kubeflow remains available through the existing manifest-preview endpoint only.

`maxRunSeconds` is the maximum accepted-run lifetime, including queue time. Omitted or zero uses 3,600 seconds; explicit nonzero values must be 60–86,400 seconds. At or after `createdAt + effective maxRunSeconds`, the controller durably requests cancellation before further work. An expired unsubmitted run is never launched. Active runs still require an observed terminal result or confirmed foreground deletion; deadlines never manufacture successful cancellation or roll back data. The limit depends on controller reconciliation and Kubernetes availability, so it is a bounded operating policy rather than an exact wall-clock or dollar ceiling. Keep namespace quotas and spending controls as separate protections. Legacy persisted profiles without the field use the same one-hour default.

Binding IDs are unique within a workspace. An explicit `allowedSubjects: []` is a valid deny-all policy for draining a binding; omitted/null subject arrays are invalid. An empty root binding array is also valid for revoking all bindings while keeping the controller running. Retain the chart’s explicit compute namespace allowlist/RBAC while draining; removing access before cancellation finishes prevents cleanup. Disabling execution or uninstalling the control plane does not cancel existing Spark applications automatically. Explicit issuer/subject grants are separate from workspace membership: an editor is not automatically allowed to use a data-access service account. Raw data access is provided only by the approved workload identity, never an arbitrary caller-supplied Spark configuration. Platform administrator privileges do not grant access to another user's runs or logs. The approved application must still enforce its data access contract. A notebook binding explicitly authorizes arbitrary Python under the workload identity, including its raw-storage and namespace permissions; this does **not** claim row-level security for arbitrary Python or governed SQL.

For explicit loopback development tests only, use `workspaceId: "default"` and the allowed subject `{ "issuer": "development", "subject": "development-admin" }`. Development persistence is ephemeral, and the standalone production controller requires PostgreSQL. Configuring any binding file, including an empty file-backed policy in development, requires Kubernetes credentials and successful discovery preflight at API startup. Without those credentials, development remains source-only; there is no development execution bypass. Handler unit tests may construct an in-memory server directly to verify queue acceptance, but that is not a supported standalone execution deployment.

## HTTP resources

All routes are under `/api/v1/workspaces/{workspaceId}`. Every operation rechecks current workspace membership. Run reads, logs, events and cancellation additionally require exact owner issuer/subject match. Editors/admins may submit and cancel their own runs; viewers can read their own existing runs. No run outputs are copied into shared notebook source documents.

- `GET /execution-bindings` returns `{items:[...]}` containing authorized public binding profiles, with no subject allowlist. Unconfigured installations return an empty list.
- `POST /runs` accepts `{bindingId,idempotencyKey}` for approved applications, or `{bindingId,idempotencyKey,notebook:{id,revision}}` for notebook bindings. Raw source, caller-supplied images, URIs, service accounts and Spark configuration are rejected. The notebook selection is required only for notebook bindings. The key is required, 8–128 characters from letters, digits, dot, underscore, colon and hyphen. HTTP 202 means durable queue acceptance, not successful backend execution. An identical key/body returns the original run with HTTP 200; conflicting reuse returns 409. Keys are workspace/owner scoped and retained with the run. Each workspace has a hard limit of 100 runs requiring reconciliation across all subjects, including nonterminal/`unknown` runs and terminal runs with unresolved source cleanup. New work above the limit returns HTTP 429 `run_capacity_exceeded`; exact idempotent replays remain available. The PostgreSQL workspace lock makes this limit atomic across API replicas. After an uncertain HTTP response, retry the exact key/body or inspect the runs list; do not generate a new key automatically.
- `GET /runs` returns the newest 200 owner-visible run summaries. To bound response size, the list omits event history (`events:[]`) and sets `eventsTruncated:true` whenever history was omitted or previously truncated. PostgreSQL projects out the history before transferring the rows; `GET /runs/{id}` and the events endpoint retain the most recent 200 events. Pagination is not implemented in this slice. `GET /runs/{id}` retrieves one run. Source bytes are excluded from both list/detail; immutable notebook provenance is included.
- `POST /runs/{id}/cancel` accepts `{}` and idempotently records a cancellation request. HTTP 202 and `cancel_requested` do not prove cancellation. The backend may complete before deletion; retain the observed terminal outcome.
- `GET /runs/{id}/events` returns `{items,truncated}` with the most recent 200 persisted state-change events. `Run.eventsTruncated` exposes the same limit; this bounded operational history is not an immutable compliance audit archive.
- `GET /runs/{id}/source` returns `{source,notebook}` for an owned notebook run. It reads the independent database snapshot after notebook edits or deletion; approved image-embedded application runs have no source resource (404). Current workspace membership and exact submitting issuer/subject are required.
- `GET /runs/{id}/logs` returns `{text,truncated}` for a verified owned driver Pod. No retained logs/backend returns a typed capability error. Driver logs are bounded and are not durably archived; the application can write sensitive data to its own logs, which therefore remain owner-scoped.

`Run` includes resource IDs/timestamps/revision, immutable `profile`, `submittedBy`, `bindingId`, `state`, `cancelRequested`, `submissionStarted`, deterministic `kubernetesName`, optional `kubernetesUid`, optional `observedAt`, `message`, `events` and `eventsTruncated`. States are `queued`, `submitting`, `running`, `succeeded`, `failed`, `cancel_requested`, `cancelled` and `unknown`. `observedAt` records the last successful backend observation; API polling and transport failures do not refresh it. The immutable profile is never re-resolved from a changed binding during reconciliation.

Status retains `executionMode: "approved-batch" | "disabled"` for compatibility. `notebookExecutionEnabled` is true when a notebook batch binding is configured; `executionEnabled` is true when any execution binding is configured. These flags describe configured capabilities, not cluster health or access for the current caller. Authorized binding discovery is authoritative. Notebook execution here means a fresh saved-revision Python batch, not an interactive kernel.

## Saved notebook source contract

A notebook binding uses `executionKind: "notebook-python-batch"`, an empty/omitted `mainApplicationFile`, a pinned runtime, and explicit issuer/subject grants. It must be provisioned in a dedicated engineering trust domain with the protected-source compute admission profile described below. Existing bindings remain fixed approved applications unless this capability is explicitly selected.

The saved current notebook must have at least one cell, all cells must be Python, and the requested positive revision must match at acceptance. A stale first request returns HTTP 409 `notebook_revision_conflict`; wrong kinds, mixed/SQL cells, invalid UTF-8/NUL source or generated source over 256 KiB return HTTP 422 `notebook_not_executable`. This is a generated UTF-8 byte limit, including source quoting and the runner, rather than a sum of editor character counts. Python syntax errors are observed job failures; they are not fabricated successful cell outputs.

Run creation locks and checks the current notebook revision, and commits a separately retained source snapshot with the run. PostgreSQL migration 003 stores it in `dataslate_run_sources`, which references the run, not notebook history. Idempotency checks occur before the notebook lookup: exact repeated binding/ID/revision/key returns the original run after an edit or deletion, while changing the selection with the same key returns 409 `conflict`. Current workspace membership and configured execution grant remain required for submission/replay.

`Run.notebook` contains `{id,revision,sha256,cellIds,bytes}`. The hash covers the exact generated Python script. Cells execute in saved order in one fresh batch process with a shared user namespace. Each is compiled separately with traceback filename `dataslate://<notebook-id>/<revision>/<cell-id>.py`; an unfinished string/block cannot accidentally consume the next cell. A private runner captures Python builtins separately from user variables. Variables/functions persist between cells within that batch; interactive state, IPython magics, partial re-execution and notebook future-compiler state are not implemented. No per-cell success/results/display artifacts are emitted by this runner.

The controller independently verifies the persisted source hash and creates an immutable ConfigMap named `ds-<run-hex>-source`, containing only `source.py`. It checkpoints `sourceArtifact.creationStarted` before an external create and records the verified artifact UID/readiness before Spark submission. `Run.sourceArtifact` exposes `{name,uid?,state,creationStarted}` with states `pending`, `ready`, `cleanup_pending`, `deleted`. Exact existing content/labels/hash/UID are verified on adoption; a known missing or replaced artifact is never recreated. An ambiguous source create can retry the same deterministic source-only operation before any Spark submission, but never retries a Spark POST.

The Spark manifest sets `mainClass: org.apache.spark.deploy.PythonRunner` and `pyFiles: local:///opt/dataslate/source/source.py`, and mounts the ConfigMap read-only only in the driver. Source is reverified immediately before the Spark POST. A verified application UID can be attached as a source owner reference using JSON Patch tests for source UID and resourceVersion; no owner change is accepted. The owner reference does **not** promise automatic garbage collection: the protected-source admission policy permits only the configured DataSlate controller to mutate/delete reserved source ConfigMaps, and `blockOwnerDeletion:false` prevents that restriction from blocking foreground Spark cancellation.

Explicit controller cleanup is durable and continues after `succeeded`, `failed` or `cancelled`. Terminal execution outcome remains separate from cleanup state. Before source deletion, the observed source UID is persisted; DELETE has UID and resourceVersion preconditions. Failed/lost deletion responses reconcile against that same identity. A never-started source can be confirmed absent, and a known UID's absence confirms cleanup. An uncertain create with no UID ever observed remains `cleanup_pending` even after a 404, since a late API create could still finish; this can require administrator investigation and continues to consume workspace capacity. There is currently no administrative resolve-unknown endpoint. Source cleanup removes the Kubernetes copy, not the independent retained database snapshot.

Install the opt-in `deploy/compute/generate.py` profile with `notebookSources:{controllerNamespace,controllerServiceAccount}` before enabling notebook bindings. Its native admission policy reserves source names regardless of labels on CREATE/UPDATE/DELETE, and removes driver ConfigMap collection-delete permission. Helm grants the controller ConfigMap get/create/patch/delete in the sticky compute namespaces; the API receives no ConfigMap access. Preserve the controller identity, admission policy and namespace permissions until all source cleanup is drained. Drivers may read namespace ConfigMaps and interfere with ordinary Spark resources; all users sharing a compute namespace must share an engineering trust domain. ConfigMaps are not credential storage, and this profile is not a hostile multiuser Python sandbox.

## Durable reconciliation and recovery

PostgreSQL migration 002 adds owner-scoped idempotency and immutable run documents, lease owner/expiry, monotonically increasing fencing token, and next-reconcile time. A controller atomically leases one due run using `FOR UPDATE SKIP LOCKED`; backend calls occur outside database transactions. The production controller reloads the mounted binding policy on every reconciliation and immediately before submission. Missing/invalid policy blocks new submission and normal reconciliation; it does not manufacture a successful run or automatically stop an existing Pod. An already recorded user/deadline cancellation may still observe and delete the owned resource using its immutable profile, namespace allowlist and verified UID, so a policy-file outage does not prevent cleanup in a running controller. A removed grant or changed immutable runtime profile requests cancellation of the affected queued or running work. Binding edits therefore revoke old runtime snapshots; they do not silently upgrade them. Kubernetes ConfigMap mount propagation is asynchronous, so revocation is effective when the controller sees the updated policy, not instantly at the API edit. This binding check does not introspect current IdP group membership; access-token expiry/revocation and binding policy have separate responsibilities. Writes require a matching live lease/fence. Concurrent cancellation is merged rather than overwritten by a worker's stale snapshot.

Before a SparkApplication POST, the controller durably records `submissionStarted:true`. Source preparation has its own separate checkpoint. An already expired operation context is checked before either checkpoint so a known inability to start does not manufacture an ambiguous submission; a crash/timeout after a checkpoint retains the conservative reconciliation boundary. Resource names are deterministic per run; the backend verifies ownership labels, runtime configuration and UID before adopting, reading or deleting anything. The observed UID is durably recorded before deletion, so a lost delete response can be reconciled. Deletion uses a UID precondition. Operator retries are disabled, so the controller is the one whole-job submission owner. This slice has **no automatic whole-job retry**.

A lost response, controller crash after its submission checkpoint, missing previously observed resource or conflicting identity produces `unknown`. Reconciliation continues to observe the same resource. It never blindly submits again after a submission checkpoint: even a 404 cannot establish that a prior job did not run and write data. This conservative boundary can require an administrator to investigate a run that crashed before its POST was sent. There is currently no manual “resolve unknown” API. Creating another run after investigation requires an explicit new idempotency key and an application-specific duplicate-write assessment.

Cancellation before submission is confirmed without a Kubernetes create. Cancellation of an observed resource is not complete until deletion is confirmed. If a submission outcome is unknown and no UID has ever been observed, cancellation remains uncertain pending investigation. Operator retention or external resource deletion can make a final outcome unavailable; an absent resource must never be interpreted as successful completion.

Migrations apply in ordered, contiguous versions under a PostgreSQL advisory transaction lock. Readiness requires the exact schema version for the binary. Newer schema versions are rejected by older binaries; rolling downgrade must follow a qualified procedure. A migration cannot be taken as backup/restore qualification.

## Release gates

Automated tests additionally cover atomic notebook snapshot/edit races in memory and real PostgreSQL, idempotency after source deletion, generated Python cell boundaries/builtin shadowing, immutable source content/UID verification, uncertain source create/patch/delete responses, terminal cleanup and operation deadlines. Automated tests cover identity grants, cross-workspace/owner denial, body overrides, duplicate concurrent create, lease exclusion/expiry/fencing, cancellation races, durable submission checkpoints, ambiguous responses, terminal outcomes, retained logs and verified Kubernetes ownership. PostgreSQL integration tests require an explicitly supplied isolated `DATASLATE_TEST_DATABASE_URL`.

A production claim additionally requires a real EKS cluster/operator, a digest-pinned compatible image, namespace admission/quota policies, IRSA or EKS Pod Identity with an explicit S3 prefix boundary, OIDC access tokens, real data correctness assertions, restart/recovery tests, measured resource limits and clean backup restoration. Row/column policy enforcement, governed SQL, ingestion connectors, notebook result publication, Sylon and the broader roadmap remain independent release gates.

A disposable local k3s `v1.35.0+k3s1` run with Apache operator `1.0.0`, chart `1.8.0` and Spark `4.1.3` executed the saved notebook fixture after editing and deleting its original notebook: the retained source produced 100 rows and sum of squares 328350. Deliberate failure, explicit cancellation and a 60-second lifetime cancellation also passed, each ending with `sourceArtifact.state: deleted` and the source ConfigMap absent. Restricted driver/executor templates, immutable source mount, per-cell traceback filenames, owner/API ConfigMap separation, 18 generic admission probes, eight reserved-source mutation probes and 11 RBAC checks were verified locally. The runtime harness uses development identity and memory persistence; PostgreSQL durability is tested separately. This does not qualify production OIDC, PostgreSQL and Kubernetes together, EKS, S3/IRSA, or an unrestricted hostile-code environment.
